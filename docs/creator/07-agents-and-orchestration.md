# 07 — Agents & orchestration

How agent presets, seats, councils, the Oracle, and delegation work, and how to add, retarget, or disable each. Sources are cited repo-relative: `packages/…` is the harness repo, `profiles/<profile>/packages/…` is the installed profile (the fork packages live there, not upstream). Read the file you are about to edit before changing anything.

## 1. Presets — the session's agent identity

- Live declaration: a `preset-<id>` row in `$PROFILE/cordis.patch.yml` (`name: '@deepseek-ai/dsh-agent-preset'`; `config.plugins` is the composition — persona, tool rows, skill dirs, each row `- id: / name: / config:`, `disabled:` takes a JS expression). The `$PROFILE/presets/<id>/` dirs (`preset.yml` metadata + `agent.cordis.yml` composition) are the pre-merge source; the merged registry does not load them.
- Shipped presets (fork, order): `orchestrator` (default implementer, 1), `sysadmin` (host ops, 2), `creator` (harness-only repair, 3); the upstream `preset-standard`/`preset-ptc`/`preset-minimal`/`preset-cordis` rows are `disabled: true`. Upstream row contract: `packages/preset/agent-preset/src/index.ts:11-20` (`id`, `name`, `description`, `order`, `plugins`), registered via `ctx.agentPresets.register`, listed by `packages/preset/agent-preset-registry/src/preset.ts` (roster + `default`/`selectedDefault`).
- Switching: the composer agent picker (`conversation.input.agent`, ui-agent-preset) switches a session's preset mid-flight (idle recomposition; a session with history refuses a new-task default swap), the header label (`conversation.session.header.actions` id `agent-preset`) names the live preset, and Settings → Agent presets sets the new-task default. `enpoi-agent-switch` reads the original preset's composition (`agentPresets.readDocument`; the pre-0.1.7 local name was `read`), freezes the original persona bytes on the agent scope, and appends the new identity + doctrine as a trailing `agent-switch` runtime-context delta (order 900), so a switch preserves the cached prompt prefix (`profiles/web/packages/enpoi-agent-switch/src/index.ts:1-23`).
- Canonical main-agent shape (cache law): every main preset declares the same composition rows in the same order — identical tool array, identical prompt sections — and the only per-agent bytes are `persona.suffix` (rendered last at order 10200) and the `enpoi-orchestration` seat label, which only resolves group pre-attach and menu visibility (the mechanism is uniform; the shipped catalog pre-attaches the creator trio to the creator seat alone). The per-preset role doctrine — the orchestrator's delegation roster, research dials, and whiteboard rules — lives in that suffix only; the shared prefix stays role-neutral. A new preset created through the authoring UI copies the base composition byte-for-byte and rewrites only the suffix, so it inherits the canonical shape automatically. `tests/preset-prompt-parity.spec.ts` guards declaration parity, the byte-identical shared prefix, and orchestrator/sysadmin menu equality (the creator menu differs only by its attached harness-authoring trio); `scripts/preset-tool-inventory.mjs` diffs the wire roster against the keyless-capture fixtures in `scripts/tool-inventory/expected-*.json` (orchestrator 50, sysadmin 50, creator 53 tools; `peer` and `debug` stay detached until attached).
- Per-seat restrictions are enforced at execution, never by tool absence: the composition mounts the same rows everywhere and the `enpoi-capabilities` pre-execute guard denies a seat's restricted calls (`SHIPPED_SEAT_TOOL_DENY` in `profiles/web/packages/enpoi-capabilities/src/policy.ts`; the document's `enpoi-orchestration.seatToolDeny` replaces a seat's list). The harness-authoring surface (`plugin_manager`, `cordis_inspect_list`, `cordis_inspect_query`) is creator-only: the `creator` tool group pre-attaches to the creator seat alone, so orchestrator and sysadmin never see the three schemas, and the seat guard backs that absence at pre-execute with a corrective reason. An operator who wants different restrictions configures `permissions.agents.<role>.tools` (doc 10, capability scoping) — but note that a permission `deny` is a *global-honesty* hide, so it also removes the tool from that agent's surface; use `seatToolDeny` when prefix parity must hold. Delegated children inherit their parent's preset, so the same guard refuses the trio for every orchestrator-/sysadmin-parented child; the child role tables name the trio (and `review_run`) so no child catalog carries a tool its guard refuses — `profiles/web/packages/enpoi-capabilities/tests/child-surfaces.spec.ts` is the guard, and the client parity spec cross-checks the same surfaces from the generated mirror.
- Create/retire: add or edit a `preset-<id>` row (copy a declaration, keep `config.plugins` minimal, add skill dirs via `skill-filesystem.config.customSkillDirs`); `disabled: true` retires it. Restart with `dsh restart --after-turn` from a hosted session (02). The **manual UI path** needs no restart: Settings → Agent presets → **+ New preset** clones a base preset — its composition, including the shared persona prefix, is copied byte-for-byte — into a new user preset with its own id, name, description, and persona suffix; Edit rewrites only name/description/suffix of user presets, Delete removes their row. Host side is `profiles/web/packages/enpoi-preset-authoring`: `presets.list|get|create|update|delete` over the fenced `/sidebar/presets` routes (`src/index.ts:1-16,240-306`); create writes through `configEditor.insert`, update through `configEditor.edit`, delete through `configEditor.remove` (`src/index.ts:54-61`) — the harness config editor (profile lock, recomposition validation, atomic write, Loader reconcile, rollback), so the picker and `agentPresets.list` see the change on the next read. `BUILT_IN_PRESET_IDS` refuse update/delete (`presets.ts:11-19,275-299`); shipped presets are edited in the profile declaration. Only the persona suffix is editable — `withPersonaSuffix` clones the plugin list and rewrites only `persona.config.suffix`, throwing when the base declares no persona row (`presets.ts:64-90`), and the UI only offers bases with `hasPersona` (`AgentPresetSection.tsx:325-333`), so the shared prefix stays byte-identical for prompt-cache parity (10). The button label is "New preset" beside one rendered plus icon (`locales.ts:100`), and the whole manual block is disabled until Coding Tools are on in General settings (`AgentPresetSection.tsx:99,122,180-193`).
- Failure modes: a composition that fails to mount is surfaced as `broken` on the roster; a row naming an unmounted plugin disables that row only. If a session "loses" a tool, diff the preset declaration's `config.plugins` against the plugin's row name before debugging deeper.

**Main-agent surfaces** (live declarations; all three mount `enpoi-tool-groups` — any group, static or on-demand, can be operator-disabled with `toolGroups.groups.<id>.enabled: false`, and the meta-tool itself with `capabilities.tools.tool_groups === false`; 05 §2/§6):

| Preset | Composition (`config.plugins`, condensed) | On-demand groups |
|---|---|---|
| orchestrator | persona, agent-instructions, first-run-context, bash/pwsh, fs, fs-search, jobs, skills (skill-filesystem + tool-skill), goal, plan-mode, orchestration (oracle, debug, tool-groups seat `orchestrator`), compaction (basic, compact, pruner), delegation (subagent `spawn` / `backgroundMode: continuable`, recovery control `send_message`/`list_agents`, workflow, ralph; fork/codex/claude-code off), ask-user, todo, web, presentation `both`, present | `peer`, `debug` — both start detached (shipped `preAttach: []`) |
| sysadmin | same rows as orchestrator (only the persona suffix and `seat: sysadmin` differ; `present` and the harness-authoring rows mounted for surface equality) | same |
| creator | same rows as orchestrator (canonical composition; only the persona suffix and `seat: creator` differ). Its doctrine stays harness-plane, and the harness-authoring rows (`plugin_manager`, `cordis_inspect_list/query`) are mounted on every main agent but runnable only on this seat (the execution guard above) | `peer`, `debug`; the `creator` group's trio is pre-attached to this seat alone (`preAttach: ['creator']`, `seats: ['creator']`) |

## 2. Main agents vs subagents

- One session = one main agent (the preset composition). A subagent is a separate child session spawned through the `subagent` tool (`packages/subagent/tool-subagent/src/index.ts`), with its own log, tool surface, and durable id.
- Specialist roster (role personas, `packages/subagent/tool-subagent/src/index.ts:366-388`; the orchestrator persona names the same four):

| Role | Fleet group | Purpose | Child-surface restriction |
|---|---|---|---|
| `fixer` | specialists | bounded implementation: precise scoped edits, builds/tests | shared deny only |
| `explorer` | specialists | codebase mapping, symbol search, tracing; reports `file:line` | loses `edit`, `write`, `str_replace_editor` |
| `librarian` | specialists | external docs/API research with citations; runs the `research` skill end-to-end (dials, archived sources, anchored claims, verification) | keeps only `str_replace_editor` denied — the shipped baseline carries the research toolset (`bash`, `read`, `grep`, `write`, `edit`, `web_fetch`, `web_search`, `skill`, `todo_write`, `custom_research-fetch`, `custom_research-verify`, `subagent`); an operator `permissions.agents.librarian.available` entry replaces it wholesale |
| `designer` | specialists | UI/UX, styling, frontend craft | shared deny only |
| `oracle` | supervision | senior reviewer; tool-only, never spawnable (`NON_SPAWNABLE_BUILTINS`, `tool-subagent/src/index.ts:400`) | n/a — its own tool protocol |

- Child instructions: a delegated child's persona is the role registry's `persona` — the settings entry `roles[<id>].persona` when set, else the shipped `ROLE_PERSONAS` text — installed as the child's `deployment:persona-prefix` system-prompt section (which shadows the parent's persona for that child and blanks the inherited `deployment:persona-suffix`) by `applyChildComposition` (`packages/subagent/subagent/src/child-agent.ts:223-258`); the Oracle never goes through `subagent` and receives `ORACLE_PERSONA` from its own tool's spawn (`profiles/web/packages/enpoi-oracle/src/index.ts:109-121,1500-1560`). Dynamic → Roles reads the same effective text from `enpoiRoles.list`, never a client copy.
- Role selection: the `role` argument is REQUIRED and is the only selection — it decides the child persona, tool surface, and model route; nothing infers it from task text (`detectSubagentRole`, `tool-subagent/src/index.ts:1145-1162`, only produces the suggestion printed in the refusal). A missing role is refused with the live roster and, when the text hints at one, the suggested id (`roleRequiredMessage`, `:438-449`); an unknown id is refused with the available roles (and the custom-role settings pointer only when the `enpoi-orchestration` document is readable, `unknownRoleMessage`, `:460-468`), while a tool-only id (the Oracle) is refused with its own `oracle_review` protocol. The role persona replaces the parent's; every child also gets `SHARED_CHILD_DENY` (`:503-540` — no delegation, councils, oracle, goals, plan mode, workflows, `ask_user_question`, `send_message`, `interrupt_agent`, `list_agents`, whiteboard mutations, and the guard-refused surfaces: the harness-authoring trio `plugin_manager`/`cordis_inspect_list`/`cordis_inspect_query` and `review_run`) and keeps the read-only `whiteboard_read` tool where the composition mounts it (`SHARED_CHILD_KEEP`, `:542-563`; the board mutations stay on the shared deny floor because `enpoi-whiteboard` refuses every child mutation). The background job controls are deliberately **not** denied: a child's bash command that outlives the executor timeout is promoted to a job owned by the child's session, the registry fences job access by owning session id, `job_output`/`job_list`/`job_kill` stay callable, and the child runtime context tells it to collect with `job_output (wait: true)` instead of re-running the command (`tool-subagent/src/index.ts:484-489`; `subagent/src/child-agent.ts:181-185`). The council seats, the Oracle review child, and the evidence research child carry the same guard-refused names in their own deny tables (`enpoi-council/src/core/fiber.ts`, `enpoi-oracle/src/index.ts`).
- Role tool surfaces are stored operator data and are audited at spawn: a name in `permissions.agents.<role>.available` or `roles[<id>].tools.available` that the live registry does not resolve is dropped with a `tool-subagent: role "…" stores unavailable tool "…"` warning (captured by `enpoi-diagnostics`) and the child spawns with the known subset, so a tool rename never bricks a role (`tool-subagent/src/index.ts:931-1100`). The code-authored `toolFilter` config keeps the strict `tools.restrict()` throw for an unknown allow name.
- Enpoi delegation rows: `tool-subagent` (`provider: spawn`, `toolName: subagent`, `backgroundMode: continuable`); `tool-subagent-control`/`list-agents` are enabled for recovery continuation (`send_message` continues a child's durable session by id); fork, codex, and claude-code rows are `disabled: true`. New work is always a fresh child session — a follow-up that repeats the task is a NEW dispatch with the full context. Recovery is deliberate: a child that stopped before its end result names its session id and stop reason in the settlement notice, and `send_message` resumes that session with its history. The Oracle stays per-query persistent (its own plugin). Per-role model routes: `enpoi-orchestration.personas[<role>]` (§3); an empty entry (the shipped default) means the child inherits the parent route.
- Two shapes (`packages/subagent/subagent/README.md:12,59`): one-shot (single result, optional structured output) and continuable (later messages, interrupt; default `backgroundMode: one-shot`).
- Context inheritance is explicit, not implied: a fork child sees the parent's completed turns, a fresh child does not — the tool description changes accordingly (`tool-subagent/src/index.ts:260-284`). Children return a result, not intermediate steps.
- `maxDepth` per delegation (`tool-subagent/src/index.ts:95-102`): omit → Host depth setting, default `1`; `0` forbids delegation; integer → provider-enforced (mount fails loud if the provider has no `depthLimit`); `'provider-managed'` leaves it to the provider. This profile overrides the Host setting to `2` with a `subagent` row in the profile patch (`maxDepth: 2`), so main(0) → librarian(1) → readers(2) works for research fan-out; readers cannot delegate further.
- Parent-controlled spawn options: provider (`spawn` = in-process), label, `run_in_background` (continuable providers resolve at inbox acceptance; one-shot backgrounds become jobs), `quiet` (no parent-facing turn noise), and `agentOptions` (provider/model/effort for the child route) (`tool-subagent/src/index.ts:1300-1470`; `subagent/src/types.ts:56`; council spawn at `enpoi-council/src/core/fiber.ts:353-369`).
- Nested children exist: a continuable child can spawn its own children, and a settled resident (nested) parent keeps the waking flow for settlement notices because a quiet hold would strand its activation (`subagent/README.md:111`).

## 3. Seats and fleet routing

- A **seat** is a named model assignment key. Seat routing lives in `enpoi-orchestration.personas[<seatId>]` = `{ provider, model, reasoningEffort?, chain? }` (read freshest per spawn, `profiles/web/packages/enpoi-orchestration` consumers; e.g. council `core/fiber.ts:274-290`).
- Fleet groups render in fixed order (`packages/client/ui-brand-enpoi/src/client/role-registry.ts:50-58`): `supervision`, `specialists`, `council`, `custom` — plus one group per registered council and `UNGROUPED` for persona-only ids.
- Shipped seats per group: supervision — The Oracle, Context Keeper, CTX Summarizer; specialists — Fixer, Explorer, Librarian, Designer; council — Referee, Chair, and each council's debaters (role-registry.ts:152-183).
- Unassigned seats fall back two ways (`fleetSeatState`, role-registry.ts:89-92): `inherit` = the dispatching/session model; `builtin-default` = the seat's own plugin route.
  - **Keeper:** always `builtin-default: freellmapi/auto` (role-registry.ts:61,157) — it runs outside a conversation and has no parent model to inherit from. Do not expect it to follow the session model.
  - **CTX Summarizer:** designated seat, always rendered, `inherit` (session model). The footer states the economics: a different summarizer model loses the prompt-prefix cache and pays full input price for the region (`AgentModelsBody.tsx:217`); the panel explains all three states — assigned / inherit / built-in default (AgentModelsBody.tsx:8-18).
- To retarget a seat: Settings → Agent Models → Fleet Routing, pick a provider/model for the row (writes `personas[<id>]`); Reset clears it back to the default. A chain assignment resolves through the `modelChains` service to its first usable member and the request carries the group id for per-request failover (compaction: `compaction-basic/src/settings.ts:206-235`; councils: `fiber.ts:238-272`).

## 4. Councils

- Two shipped councils, data-defined specs (`profiles/web/packages/enpoi-council/src/profiles/`):
  - **roundtable** — Skeptic / Architect / Pragmatist debate a decision; ledger kinds `crux` (C-, terminal `invariant|falsified|dissent`) and `risk` (R-); mandatory steelman before an attack flip; deliverable sections Decision / Options Considered / Evidence / Established Invariants / Binding Dissents / Action Items; defaults `defaultMaxRounds 6`, `stagnationLimit 2`, `challengeRound true` (`roundtable.ts:31-57`).
  - **chorus** — Visionary / Experiencer / Integrator in forest mode (SPROUT/BRANCH/FUSE/TENSION, nothing deleted); topological-saturation stopping; harvest with lineage (`chorus.ts:31-56`).
- Every council runs with two fixed arbiter roles, never seats: `referee`, `chair` (`enpoi-council/src/registry.ts:37`). Seat ids must be 2–32 chars `[a-z0-9_-]`; 2–8 contenders (`core/spec.ts:141,214`); ledger transitions are a DAG enforced by the engine, not the model (`spec.ts:51-64`).
- Tools: `roundtable` and `chorus` (one per enabled council), plus `council_register` / `council_list` (`tools.ts:174-176,256,421,522`). Registered councils get a tool named by their id.
- Running a council: the tool call is blocking; params come from `enpoi-orchestration.parameters.council`, read fresh per run (hot-swap) — `defaultMaxRounds` (6), `debaterTimeoutMs` (300 s), `runDeadlineMs` (30 min, on breach it skips to the chair), `evidenceBroker` (true), `evidenceTimeoutMs` (120 s) (`params.ts:22-38`; clamps at 48-62).
- **Evidence broker + vault:** debater fibers deny all retrieval tools and `bash` (`core/fiber.ts:93-149`, keep-list only whiteboard tools + `send_message` denied); a seat asks for ground truth with `NEED_EVIDENCE(target:, question:)` text lines. At each epoch boundary the engine batches the queue into ONE research child (`explorer` for codebase targets, `librarian` for external), one `SHEET n / CITATION / FACTS / CONFIDENCE` per question, committed to the append-only **evidence vault** as `F-n` before the referee pass (`core/broker.ts:120-132,193,236-245`; `core/vault.ts:10-18`). Missing/excess sheets are named failures, never silent; placeholder citations degrade to `unverified`.
- **Referee:** one flagship fiber per pass returns strict JSON only — `admissions`, `flips`, `directives`, `floor`, `scopeWarnings` (`core/referee.ts:78-94`). The engine applies every mutation and rejects steelman-less attack flips procedurally (`referee.ts:252-270`), unknown ledger kinds with a named reason (`referee.ts:289-296`), and a pass with no JSON is a hard handoff failure (retry once).
- **Chair:** compiles the deliverable with EXACTLY the spec's `deliverableSections`; a missing/bodyless section is a reported `ChairOutputError`, retried once, then mechanically compiled — never an empty answer forwarded (`core/chair.ts:1-21,58-84`; `core/engine.ts:544-567`).
- Register/retire a council: write `enpoi-orchestration.councils[<id>]` (same shape `council_register` validates; `stoppingPolicy` + `chairTemplate` required) or use `council_register`. A settings entry with a built-in id overrides it; `disabled: true` retires it (tool disappears) — `registry.ts:1-19,306-335`. Invalid entries stay visible with their exact validation problem in the council UI; nothing is skipped silently.

## 5. The Oracle

- `oracle_review` consults a senior reviewer child: call #1 of a user query is fresh and self-contained; follow-ups are deltas in the same fiber. Blocking by default, `background: true` delivers the verdict as a message (`enpoi-oracle/src/index.ts:1123-1165`).
- Lifecycle: fiber resets at each new human user message; one consultation per session at a time (single-flight mutex returns `CONCURRENT_CALL_REJECTED`); timeout default `120_000 ms` via `parameters.oracle.timeoutMs`, resolved per call; on timeout the child is NOT cancelled and its verdict is delivered late as a message (`index.ts:505-518,1415-1560`).
- Surface: read-only review; call #1 and each changed-board delta include a bounded derived whiteboard view (`dsh-enpoi-whiteboard`), so the reviewer sees the operator's pinned context without a board mutation. The oracle may delegate (subagent tools) and use `request_evidence(target, question)`, which spawns one research child and returns a cited fact sheet (`index.ts:107-135,1214-1270`). Verdict JSON `{approved, concerns, unverified, blockers}` must be last (`index.ts:118`).
- Model: `personas.oracle` (provider/model/effort/chain). With a chain, a failed attempt disposes the child, respawns the SAME initial package on the next link, and fails open to exactly one wait without a chain (`index.ts:622-680,1415-1500`).

## 6. Delegation rules

- **Dispatch doctrine (orchestrator persona suffix):** scoped, simple, clearly implementable work goes to a `fixer` readily — the orchestrator keeps the complex reasoning, research, context, and understanding, and uses the fleet liberally so its own context stays lean. Dispatches are background by default; `run_in_background: false` only when the very next step needs the answer. Parallel work is one `subagent` call per specialist in the same assistant message — several specialists at once, even several of the same role. New work is always a fresh, self-contained dispatch; a follow-up to a finished task is a NEW dispatch carrying the full context, including what the previous child reported and what has changed. Continuation by id is for recovery, not a second dispatch lane: a child that stopped before its end result names its session id and stop reason in the settlement notice, and `send_message` continues that session with its history when its context is worth resuming. While children run the operator keeps interacting; the parent ends its turn with a short report of what it dispatched and what each child should return.
- **Role charters (the four spawnable specialists):** `fixer` — scoped implementation, bug fixes, focused edits, builds and tests; `explorer` — codebase mapping, symbol search, file discovery (never mutates); `librarian` — web search, documentation, library research, external APIs, reported with citations; `designer` — UI/UX, responsive styling, design-system tokens. Pass the role explicitly in the `subagent` call's `role` argument (`"librarian"`, `"fixer"`) — that is how the child receives its persona. Prefixing the dispatch description (`"librarian: research X"`) only helps the refusal suggest the role if the argument is ever omitted; the live roster is authoritative, so never search the repository or harness sources to discover which agents exist.
- **Whiteboard & context (orchestrator-owned):** before dispatching several children or any long-running task, the orchestrator authors and pins what the fleet must not have to repeat — current task state, key decisions, invariants, file paths — with `whiteboard_write`/`whiteboard_pin`, and updates or unpins as work lands; a tight board replaces repeated context in every Task Card. Children read the board but never author it (lineage gate enforced); the background context keeper maintains session checkpoints on its own, so neither parent nor child duplicates a brief by hand. Board storage, scope resolution (global → project → parent session → session), and stale flags: 08.
- **Programmatic tool execution (run_code):** for batch operations, loops across files, or data transformations, call `run_code` to execute a TypeScript program in ONE turn instead of serial turn-by-turn tool calls. Subagents (`fixer`, `explorer`) also have `run_code` available natively. Three key conventions: (1) each call runs in a fresh isolated Node process — no state carries between calls, and never park state in `/tmp`; (2) erasable TypeScript only (no `enum`, namespaces, or runtime-only TS syntax); (3) arguments must be lossless JSON — do not pass `undefined` inside objects (rejected outright by the bridge).
- **Research delegation (this profile):** anything needing the live web — news, pricing, docs, comparisons, releases, "what is the latest…" — goes to ONE `librarian` with the question and a dial: `lookup` (1–3 fetches, inline, <1 min) / `quick` (2–4 sources, short cited answer) / `standard` (default: 5–10 sources, 1–2 readers, cited report) / `deep` (15–25 sources, 3–6 readers, dossier) / `exhaustive` (deep + adversarial counter-searches). The dispatch prompt names the question, the dial, the freshness horizon, the source/time budget, and the deliverable (`librarian: research — <question>`; template in `$PROFILE/skills/research/SKILL.md`). The librarian runs the `research` skill end-to-end — archives sources with `custom_research-fetch` (the page text never enters the caller's context), writes anchored claims, runs `custom_research-verify` to PASS, and returns the cited answer plus the run-dir path. The main session never fetches, saves, or extracts; deep and exhaustive runs fan out reader children under the librarian.
- **Budgets:** every delegated child gets a standing clause — `CHILD_TOOL_BUDGET = 20` tool calls is a ceiling for exploration, not a counter to satisfy; report best evidence or report what is missing (`packages/subagent/subagent/src/continuation-messages.ts:104-125`). The clause is appended on every path (continuable, background, foreground — `tool-subagent/src/index.ts:1193,1212`).
- **Lifecycle (spawn → run → settle):** spawn validates the role and provider capabilities, snapshots the delegated permission state, and appends a `subagent/catalog` fact to the parent after admission (one-shot after the provider returns, continuable after inbox admission — `subagent/README.md:113`); a failed spawn rolls back unpublished resources and publishes no catalog fact. Run happens in the child's own durable session/log; background (continuable) is the default, `run_in_background: false` waits and returns the report in the tool result. Settle injects the one notice.
- **Ceilings:** `maxDepth` (host `subagent` settings default `1`; this profile sets `2` — main → librarian → readers; a tool row may set an integer or `provider-managed`, `0` forbids delegation), `maxActiveSubagents` default `8` live continuable children (capacity refuses with `ACTIVATION_LIMIT_REACHED` and does not queue — wait for a settlement notice before retrying; slots are process-local — `subagent/README.md:47-55`), plus the 20-call budget clause. The orchestrator persona suffix states the same doctrine (8 live children, not queued, track settlement notices / `list_agents` running rows), and the rejection text repeats it (`packages/subagent/subagent/src/continuation-activation.ts:43-51`).
- **Quiet single delivery:** foreground delegation returns one result; background/continuable settlement injects ONE notice into the parent containing the outcome line and the child's closing report only (reasoning and tool blocks stripped) — `continuation-messages.ts:212-318`. A settlement that lands while the parent is parked/reverted is held quietly in the durable next-turn inbox for a root parent (`subagent/README.md:111`). A turn abort (`cancel`) clears only **user-sourced** inbox items; settlement notices, adjacent-agent relays, and job-completion notices already spliced into the inbox survive to the next turn, each user input canceled with its own durable record and no auto-wake (`packages/core/agent-loop/src/inbox.ts:100-115`; regression `packages/subagent/subagent/tests/cancel-preserves-settlement.spec.ts`).
- **Recovery continuation (this deployment):** children do not stream intermediate steps back, but the control tools are enabled. A child that stopped before its end result names its session id and stop reason in the settlement notice; `send_message` to that id cold-resumes the same durable session with its full history (an idle child; a working one receives the message at its next step). `list_agents` lists a parent's continuable children by id, bounded: `status`/`query` filter the matching set (query matches id or label case-insensitively), `limit` defaults to 20 and is capped at 100, `offset` pages the rendered text, rows order running-first then inactive most-recent-first (descendants keep tree pre-order), and a paged footer names the displayed range, the running/inactive split, and the next offset; the structured result inside `run_code` still carries every matching row (`packages/subagent/tool-subagent-control/src/list-agents.ts:25-28,80-123,239-312`). New work is still a fresh dispatch — continuing an old child is the deliberate exception for recovery or an operator-requested follow-up, never the default path for a new task. The Oracle keeps its own single-flight mutex (one consultation per session at a time).
- **Stopping:** the composer's Stop (✕) is `detach` — the turn stops, live continuable descendants keep running; "Stop all agents" is `stop-all` — `enpoi-cascade` interrupts every live continuable descendant under ancestor authority; a revert interrupts only descendants spawned inside the reverted span. Interrupt is PARK-semantic (current turn cancelled; activation stays resident). A parked worker resumes when the parent `send_message`s its id with the next instruction; the human can also continue it from its sidebar chat tab (host Queue/Steer prompt).
- **Approvals:** a child's ask forwards to the nearest live root (04 §6); the child's scope is fixed at spawn and cannot widen from inside (the delegation-scope statement, `subagent/README.md:169`).
- **Nested children:** depth is capped by `maxDepth` (shipped default 1; this profile 2, see §2); stopping a parent parks the descendant tree — the cancel cascade recursively enumerates the whole session tree, including continuable grandchildren (`profiles/web/packages/enpoi-cascade/src/index.ts:58-114`).
- **Failure forwarding:** a failed child never reports success — `settlementSummary` names the ending (aborted / max-tokens / refusal / error / abnormal) and, for every unfinished ending, the session id to inspect or continue; providers append the failure detail plus any preserved partial answer to the error (`continuation-messages.ts:212-318`; `tool-subagent/src/index.ts:171-180`).
- **Keeper exemption:** the context keeper is not a subagent, so the ancestor-cancel cascade never enumerates it — it keeps running through stop-all/revert cascades (`enpoi-cascade/src/index.ts:21`; doc 34 invariant I9).

### Settlement, stopping, and goal rounds

- **Settlement notices:** a background continuable child's result arrives as one runtime-owned user-role message with source kind `subagent-settled`. While the parent runs it is steered at the next step boundary; an idle parent is woken with it queued as its next turn. The notice is the authoritative end of the dispatch — `list_agents` can only report the coarse `running`/`inactive` activity that the notice supersedes, and the third consecutive identical listing draws the repeat-tool reminder.
- **Bounded reports:** `settlementReportMaxChars` (default `12000`) and `settlementReportMaxImages` (default `4`) on the host `dsh-subagent` row bound the closing report copied into each notice, sampled per notice. A report inside both bounds is copied byte-identically; a larger one keeps a surrogate-safe head and tail and its first images, followed by one line stating the exact omitted character and image counts, naming the child's durable session, and naming `session_event_search` / `session_event_read` to read the full report there. The complete report always stays in the child's own session.
- **Goal rounds:** the round driver queues a round only when the session is idle and the goal is armed, and it waits for every running descendant (`subagents.waitForTreeWork`) before reserving one. A parent that ended its turn to await settlements therefore receives their notices before a round is charged, and a session that is no longer idle or is disarmed after the wait skips reservation.
- **Stop vs stop-all:** the composer's Stop aborts the turn and revokes queued goal rounds and pending human prompts (peer prompts enter as source kind `user`, so a Stop clears them too), while settlement, job, and relay observations stay pending for the next turn. Stop-all additionally parks every settlement that lands before the operator's next turn — a child that finished naturally while its interrupt was in flight — so the stop opens no waking turn, and that next human turn claims each parked report once; a nested resident parent keeps the waking flow.
- **Detach:** the composer Stop is `detach`; live continuable descendants keep running, and their settlement notices wake or steer the parent normally later. Stop-all interrupts the descendant tree under ancestor authority instead.
- **Child identity and discovery:** a child's durable identity is its `SessionId` only — there is no role-keyed reuse, so a fresh dispatch is the default and `send_message` continues a recorded id only for recovery. One-shot children are not continuable: `send_message` cannot resume them and `list_agents` omits them; a continuable `run_in_background: false` child remains listed and resumable. `list_agents` takes the `status` (`running`/`inactive`) and `query` (id or label, case-insensitive) filters plus `offset`; `limit` (default 20, max 100) bounds only the rendered text, and `run_code` receives the full matching array.
- **Large fan-out:** capacity stays 8 live continuable activations and a refused dispatch is not queued (`ACTIVATION_LIMIT_REACHED`). For a fleet in the ~150-child range, dispatch in waves of at most 8, keep a dispatch ledger (child id, task, expected report) in the parent or on the whiteboard, never poll (the settlement notice wakes you), ask each child for a concise report, and filter with the `list_agents` filters or inside `run_code` instead of paging through rendered lists.
- **Restart limit:** the settlement outbox is process-local, so a restart can drop a pending notification; the child's report remains in its own session, and the parent catalog records too little to rebuild the notice. A held notice also does not survive a host that unloads before delivering it.
- **Goals are model-driven:** `create_goal`, `get_goal`, and `update_goal` are the surface (`tool-goal`, mounted per preset); the `dsh-web-app` bundle disables the `command-goal` row and no shipped preset mounts it. `blocked` is refused until at least `blockedAfterConsecutiveRounds` rounds have started (default 3) with the wording `blocked requires at least N goal rounds started in this goal`. Resume stays a human action: the goal bar shows Resume only while `roundsStarted < maxGoalRounds`, and the service refuses a resume once the budget is exhausted (default cap 256 rounds).

### Tier workflows

The operator invokes a guided workflow by asking for a tier (for example "tier 1" or "tier 3") in the request; the skills are operator-editable data at `$PROFILE/skills/tier{1,2,3}-workflow/SKILL.md`, read per request — edit the file and the next request sees it (no build, no restart), and `enpoi-orchestration.capabilities.skills['tier1-workflow']` (etc.; §8) removes or restores the skill in the catalog. Scope is per request: a tier governs the current request only, a new request starts from the default behavior unless the operator invokes a tier again, and invoking another tier for the same task replaces the active workflow. State lives in harness-native artifacts — whiteboard entries (`whiteboard_write` / `whiteboard_pin`, visible to spawned children) plus the `todo_write` list.

- **Tier 1 (supervised):** Oracle review of the drafted plan (`oracle_review`) before any code, implementation, then a final Oracle consensus before shipping — actionable issues are fixed first.
- **Tier 2 (ideation → plan):** mandatory `roundtable` on the vision, its council report translated into a technical plan, Oracle review of that plan, implementation, then a final Oracle review.
- **Tier 3 (all-out):** continuous Oracle supervision across implementation milestones, plus a mandatory `roundtable` whenever ambiguity blocks the path.
- All three tiers carry a **Delegation & Offload** section: keep the main session lean, dispatch bounded work to `fixer`/`explorer`, route web research to ONE `librarian` with a research dial (standard default), and give every dispatch the full context it needs (fresh session, self-contained brief).

## 8. Enable / disable switches

- Capabilities Control Center (`enpoi-orchestration.capabilities`) is the master switchboard (`profiles/web/packages/enpoi-capabilities/src/state.ts`, `types.ts:44-70`): `skills[<name>] !== false` strips a skill from the catalog AND shadows it pre-dispatch; `tools[<id>]` false strips the tool from the model-facing list and denies it; `mcp[<id>] === true` is required to mount an MCP server.
- Protected infrastructure cannot be disabled: `enpoi-contracts`, `enpoi-context-keeper`, `enpoi-cascade`, `enpoi-living-brief`, `read`, `glob`, `grep` (`types.ts:27-35`).
- The keeper's own tool flag is `capabilities.tools.keeper` (default true); disabled means prose distillation and claims extraction are skipped and consumers degrade to the deterministic fold (`enpoi-context-keeper/src/index.ts:102-113,586-588`).
- A registry role is hidden from the fleet with `roles[<id>].seat: false` or `disabled: true`; `null` deletes it (`role-registry.ts:203-261`). A role may carry `tools.available` (a tool-id allowlist for its persona, `role-registry.ts:253-257`) — a per-role availability layer on top of the profile defaults and before session overrides. A tool-only role (Oracle, `spawnable: false`) is never matched by delegation text (`tool-subagent/src/index.ts:340-350`).
- **MCP on-demand:** a catalog server's `mode` defaults to `always-on`; `on-demand` servers are never auto-connected (`profiles/web/packages/enpoi-capabilities/src/index.ts:87-99`; `mcp-mounts.ts:91-97`). The agent mounts one for its own session with the `mcp` tool — actions `list` / `mount` / `unmount`, `server` is the catalog id (`index.ts:761-813`); its shipped policy row is `allow` because `list` is read-only and mount/unmount only touch servers the operator already configured and allowed, scoped to the calling session and reversible — the mounted server's own tools keep their own rows (`policy.ts:169-173`). One shared mcp-client fiber per server serves every session that mounted it, and it disposes only when the last session unmounts (`index.ts:556-618,653-666`); each session's mounted set is durable (`mcp/mounts` event → `mcpMounts` projection, `mcp-mounts.ts:32-77`) and is released at session end (`index.ts:710-724`). An on-demand server this session has not mounted is filtered from the advertised surface (`index.ts:419-450`) and denied at pre-execute as the backstop for in-flight turns (`index.ts:1361-1376`). Doctrine: "a mount made for continuing work stays mounted; a one-shot errand unmounts when it is done; when unsure, leave it mounted" (`index.ts:858-866`). A skill's `mcp: [server]` frontmatter mounts on load (`index.ts:814-855`); the session header chip lists this session's mounts and unmounts from its popover (`$REPO/packages/client/ui-brand-enpoi/src/client/McpMountsChip.tsx:1-7,124-160`).
- **Permissions matrix presentation** (09): the Permissions window reads every live registered tool name and folds families derived from the shipped tool-group catalog — one aggregate row per enabled group with at least two same-policy members (Goals, Councils, Jobs, Workflows, Whiteboard, Memory, Recall, Peer interconnect, Debug & observability, Creator (harness authoring)) — while a member whose shipped policy differs stays its own concrete row; it labels the `mcp` tool "MCP servers (mount / unmount)", folds every concrete `mcp__<server>__<tool>` under its server row, and renders "All MCP tools" as the derived aggregate master (the master and each family own no settings key; their chip fans the chosen policy out to the concrete keys) (`$REPO/packages/client/ui-brand-enpoi/src/client/permissions-model.ts:319-362,434-472`). The matrix also lists custom-tool rows automatically from the live registry (05 §8).

## 9. Failure modes → fix

- **Evidence:** incidents in `$DSH_HOME/diagnostics/incidents.sqlite` (sources: logger sink, plugin lifecycle FAILED, session-event error paths, client reports; `diagnostics_report` folds them with stable codes/fingerprints — `profiles/web/packages/enpoi-diagnostics/src/index.ts:6-13`); per-plugin logs `$DSH_HOME/logs/enpoi-*.log` (cascade, keeper, council, git, file-revert, runtime-probe) plus `$DSH_HOME/logs/startup-*.log`; service stdout in the journal. The Cordis logger only buffers, so plugin diagnostics are those files.

| Symptom | Cause | Fix |
|---|---|---|
| Seat runs on an unexpected model | No assignment → inherit, or stale `personas[<id>]` | Agent Models → Fleet Routing: assign or Reset the row; check the row's state label |
| Council tool missing | Council retired (`disabled: true`) or invalid entry | Council list shows the validation problem; fix the spec or remove `disabled` |
| Council produces empty deliverable | Chair output failed shape validation and mechanical compilation also failed | Check the council log (`$DSH_HOME/logs/enpoi-council.log`); inspect ledger/referee records in the result |
| `oracle_review` blocked (`CONCURRENT_CALL_REJECTED`) | Another consultation in flight for the session | Wait for the verdict or the timeout; the child is not cancelled |
| Child floods the parent with messages | a child calling `send_message` per finding | children keep `send_message` denied (`SHARED_CHILD_DENY`), so intermediate traffic cannot happen; the 20-call budget clause is appended |
| Keeper still runs after stop-all | Cascade exemption (by design) | Disable it via `capabilities.tools.keeper` if truly unwanted |
| Preset missing after install | `preset-<id>` declaration absent or `disabled: true` | `dsh plugin list`/`cordis_inspect` for the row; see 02-install-and-update |
| Child fails to start | role unknown/tool-only, provider capability missing (`continuable`, `depthLimit`), or capacity `ACTIVATION_LIMIT_REACHED` | read the tool error verbatim (it names the role list or capability); `session_debug` digest → recent tool calls; `diagnostics_report`; check the preset declaration's delegation rows |
| Child stuck (running, no progress) | long turn, waiting on an approval, or a parked activation | `session_debug` digest (`state.activeDescendants`, `subagentTree`); Subagent Sessions tab; QueueDock; then Stop all parks it — `$DSH_HOME/logs/enpoi-cascade.log` names refused interrupts |
| Approval not forwarded | root not live, root mode not interactive/full-access, or the ask undeliverable (fails closed) | 04 §6; `session_debug` `pendingInteractions`; Live Debug ask buttons; confirm the root session is open |
| Tool missing for a role | on-demand group not attached, capability disabled, role allowlist/deny, or the preset row unmounted | `tool_groups list`; 05 §4/§9; `enpoi-orchestration.roles.<id>.tools.available`; diff the preset declaration |

| Custom tool fails or asks on every call | malformed record/placeholder, or the `custom_<id>` permission row inherited `ask` | read the plugin stderr line; fix the record in Dynamic → Skills & tools; set the row in Permissions (05 §8) |

## 10. Device-to-device & peer-to-peer agent communication

The peer API lets an agent on one machine drive a paired session on another harness instance. It is a narrow session API, not a remote shell: every call resolves through the serving host's `pairings.yaml` and maps onto `session.*` behind a closed dispatch table, so `settings.*`, `credentials.*`, `fs.*`, and `control.*` are never re-exposed (`packages/api/peer/README.md`). There is no authentication on the peer path: a pairing's optional `token` is parsed and the caller sends it as a bearer header, but the host verifies nothing from it, so binding this surface to a tailnet or trusted LAN is the security assumption. Treat the pairing file as the access-control document, never the token.

### Namespace, tools, and CLI

- Serving namespace: `@deepseek-ai/dsh-api-peer` registers `ctx.peerService` with the `peer` Typert namespace — `handshake`, `list`, `create`, `prompt`, `follow`, `page`, `state`, `cancel`, `answer`, `models`, `selectModel`. Unary calls ride the gateway's HTTP envelope; `follow` is a WebSocket stream. A loopback caller passes the gateway launch-token cookie; a tailnet caller needs no credential while the no-auth assumption holds.
- Handshake capabilities: `state-latch`, `derived-latch`, `assistant-stream`, `answer-routing`, `runaway-ceiling`, `session-create`, and `model-attribution` are advertised unconditionally; `model-discovery`, `model-routing-at-create`, and `model-switch` appear only while a `peerRouting` service is mounted; `token-ceiling` appears only while the token meter is mounted (it registers the durable `tokenUsage` projection). The advertised set is computed per handshake call, so a host withholds a capability whose service is not mounted instead of promising a call it would refuse.
- Caller tools: `dsh-enpoi-peer-bridge` registers eight model-facing tools in the on-demand `peer` group (label "Peer interconnect", never pre-attached): `peer_status` (handshake, exposure, latch, active descendants, next-request model, last turn end, pending asks; the CLI form also prints the budget), `peer_sessions` (bound remote session id, latch summary, last activity for every caller-role pairing; read-only), `peer_models` (policy-filtered chains and models, with each member's live state — `ready`, `cooldown` with `cooldownUntil`, or `deprecated` — and the pairing policy echoed), `peer_switch_model` (idle-only route switch), `peer_ask` (create/adopt, prompt, follow to a terminal), `peer_asks`, `peer_answer` (approval `allowed-once`/`rejected`, or question selections; `allowed-always` is not grantable from a peer), and `peer_cancel`.
- CLI: `ds peer` is `scripts/dsh-peer.mjs` (the installer seeds it as `dsh-peer`). Commands are `handshake <endpoint>`, `status [alias]`, `list [alias]`, `models <alias>`, `switch <alias> <provider/model>` or `switch <alias> --chain <id>`, `ask <alias> <message>`, `follow <alias>`, `asks <alias>`, `answer <alias> <askId> <once|reject>` (or `--select <label>`), and `cancel <alias>`. `models` takes `--cursor`, `--limit`, `--zero-price`, and `--tools`; `switch` takes `--effort` and a reusable `--request-id`; `ask` takes the create-only route flags `--model <provider/model>`, `--chain <id>`, `--effort`, and `--max-tokens`, and a same-message retry reuses the requestId persisted under the pairing directory instead of queueing twice.

### Pairings, the routing policy, and strict parsing

- `$DSH_HOME/pairings.yaml` (0600, reloaded when its mtime or size changes) is generated by `dsh update` from the profile fleet registry `profile/web/fleet.yaml` through `profile/web/scripts/generate-pairings.mjs`; devices change only through the update path, and a first-line `# dsh-managed: false` marker hands the file back to the operator. `$DSH_HOME/peer-state.json` (0600, atomic replacement) holds the machine-written bindings.
- A fleet member may carry a `routing` block; the generator stamps it into that alias owner's pairing entry and validates it with the peer parser's own rules. The shipped human entries (`serverlocal`, `pc`, `macbook`) carry none.
- `routing` fields: `allowChains` (exact chain ids, never globs), `allowModels` (patterns over `provider/model` with `*` as the only wildcard — any run of characters, `/` included, anchored at both ends), `requireZeroPrice`, `requireNoTraining`, `requireTools`, `allowReasoningEfforts`, `allowSwitch` (`never` default, or `idle-only`), and `maxTotalTokens`.
- An absent `routing` block keeps the legacy behavior: create/adopt routing is gated by `allowModelChange` (default false). A present block is authoritative: every create and adopt must name `provider`+`model` or a `chain`, the policy is evaluated before any session or selection exists, and a refusal leaves no session and no binding behind. The applied selection is the routing service's resolved verdict, so a chain-only request is resolved there.
- Fail-closed evaluation: every chain member is rechecked at selection time against `allowModels`, the price, training, tools, and effort policies, so a dynamic chain that drifted to include a route the policy refuses (gated, deprecated, paid under a zero-price policy, or outside `allowModels`) is refused; a gated or deprecated route, an unknown route, an unprovable price (`price-unproven`), unproven training data, and unproven tool support are all refusals when the policy demands that proof. A pinned route must match an `allowModels` glob, so a policy with no `allowModels` selects only chains; a chain id must be listed in `allowChains`.
- Strict parsing: unknown keys at the pairing, `create`, and `routing` levels, wrong value types, empty patterns, and patterns outside `[A-Za-z0-9._:/@*+-]` fail the load. A rejected reload keeps the previous valid snapshot and logs one bounded warning per distinct diagnostic (first line only, at most 300 characters, capped at 16 distinct messages per store); a malformed first load fails the host loud.
- Exposure is required per entry (`answer-only` or `debug`) and is chosen host-side; a caller cannot request it. `answer-only` carries the dialogue, turn boundaries, approval audit, and settlement notices; `debug` adds tool/step/subagent/goal/compaction/revert records. The `assistant-stream` opt-in requires `debug` and is refused with reason `exposure` otherwise.
- The routing service is the profile plugin `enpoi-peer-routing`, mounted through `dsh.profile.bundles`; it provides `ctx.peerRouting` and stays inert until a pairing carries a policy. Discovery and evaluation share one predicate, so `peer_models` cannot list a route the policy would refuse.

### Model attribution, switching, and the token ceiling

- `peer.state` and `peer.follow` report the route that actually answered: `lastTurnEnd.ran` carries `{ provider, model, chain?, hops, usage? }`, folded from the answering `assistant/message` source and the failed attempts inside that turn. `hops` counts failed attempts; `usage` is the answering message's own four buckets (`inputTokens`, `outputTokens`, `cacheReadTokens`, `cacheWriteTokens`). `state.model` stays the Session's next-request selection, so a rolling chain can make it differ from `lastTurnEnd.ran`.
- Each durable `llm/attempt-failed` also yields one synthetic `model-hop` record `{ from, to?, reason, chain?, at }` at the source event's seq, in every exposure, with a closed reason vocabulary (`rate-limit`, `error`, `cooldown`, `unavailable`) and no provider prose, status, or requestId. `state.recentModelHops` keeps the newest 32 oldest-first; older hops stay readable through `follow`/`page`.
- `peer.selectModel` switches one idle session's route for its next turn (`persistDefault: false`). A running or waiting session refuses with `peer/conflict` reason `busy` and the latch; a cold session counts as idle only when its agent is not running. Every call needs a `requestId`, deduped by a payload hash: a replay returns the original value with `replayed: true` (before the idle check), and the same id with a different payload is `peer/conflict` reason `request-id-reuse`. The model-change attribution is process-local and not durable.
- Token ceiling: `maxTotalTokens` on a create is capped by the pairing policy's ceiling when it sets one (above it → `peer/forbidden` reason `budget`; omitted → the policy value) and recorded on the binding. The host enforces it responsively: a request already in flight finishes, the watcher stops the turn after the crossing response commits (or the next turn that starts while the session stays over budget) through the Agent's cancel with the durable hook cause `{ kind: 'hook', reason: 'peer/budget' }`, and the terminal reports `stop: 'budget'`. Later peer prompts are refused with `peer/forbidden` reason `budget`; `peer_answer` and `peer_cancel` stay allowed because they spend nothing new. A host that cannot read the usage projection refuses any create carrying a ceiling with reason `budget-unmetered`, and `state.budget.metered` is false whenever usage could not actually be read.
- Measured cost: a tool-using orchestrator turn costs about 13–17k input tokens, dominated by the tool schema, so a ceiling below ~40k can be crossed by one turn; the crossing request still finishes first, so the stop lands after that answer is delivered.
- Error vocabulary: the closed peer codes are `peer/not-paired`, `peer/not-found`, `peer/forbidden`, `peer/conflict`, `peer/gap`, `peer/hop-limit`, `peer/version-skew`, and caller-side `peer/target-unreachable`. `peer/forbidden` carries a reason — `routing-required`, `routing-not-configured`, `routing-unavailable`, `model-change`, `switch-not-allowed`, `exposure`, `budget`, `budget-unmetered`, or a routing verdict (`model-not-allowed`, `chain-not-allowed`, `price-unproven`, `training-unproven`, `tools-unproven`, `effort-not-allowed`, `unknown-route`) with the refused identifier in `denied`. `peer/conflict` covers a busy session (`busy`), a reused requestId (`request-id-reuse`), and an ask another participant already settled (carrying its `askId`); `gateway/bad-request` covers malformed arguments and an invalid discovery cursor. The caller bridge adds `peer/capability-missing` locally when the remote handshake lacks the capability a tool needs, so that code never crosses the wire.

### What a remote controller can and cannot do

| Operation | Peer path |
|---|---|
| Handshake, list exposed pairings, read latch/state | Yes — `handshake`, `list`, `state` |
| Create or adopt a session under an alias | Yes — `create` where the pairing declares a `create` block |
| Prompt a paired session, follow its turns, page history | Yes — `prompt` (always queued), `follow`, `page` |
| Cancel the active turn | Yes — `cancel`, attributed to the peer |
| Answer a pending approval or question | Yes — `allowed-once` or `rejected`, or question selections; never a standing allow |
| Discover and select models | Yes — `models` and idle-only `selectModel`, within the pairing policy |
| Enumerate arbitrary local sessions | No — `list` reports only pairings, and a target outside the pairing gate is `peer/not-paired` |
| Edit settings, providers, credentials, files, or permissions | No — the namespace maps only onto `session.*` |
| Grant a standing allow | No — the peer answer vocabulary has no `allowed-always` |
| Steer a running turn mid-step | No — `prompt` queues; a human prompt preempts the peer |
| Run a sessionless task | No — every prompt targets a paired session, and `create` binds one |

### Limits

- One live binding per alias: an alias resolves to its pinned `sessionId` or the newest `create` binding, and a replaced binding moves to the retired list and stays addressable only by explicit `sessionId`. N concurrent workers therefore need N aliases; `peer.create` has no idempotency key, so a retry after a lost response creates another session and rebinds — reconcile through `peer.list` and the binding state before retrying.
- Pending asks live in the host's in-memory registry: a restart drops them and the peer sees the interrupted terminal plus `idle`. Held settlement notices are also process-local and may be lost on restart; the child's report stays in its own durable session.
- A human Stop clears queued peer prompts (they enter as source kind `user`) before they become durable `user/message` records; a caller that saw `accepted: true` must detect that its requestId never reached the log and re-drive it.
- `peer.models.models` is empty when `allowModels` is absent or empty even with ready chains, so read `chains[].members` for the chain-selectable set. No cost is ever reported — `budget` is a token ceiling only.

### Testing recipe between devices

1. Ensure both devices have the harness running and reachable (e.g. over Tailscale), then add or edit the members once in the profile fleet registry (`profile/web/fleet.yaml` in the harness repo or profile source, so the change rides `dsh update`): `hub` names the hub member, and every member carries `name`, `exposure`, `create` (default `orchestrator`), hostname match patterns, and a fallback tailnet `ip`; a member may also name a `port` (default 3080) and a `routing` block.
2. Run `dsh update` on each device. The generator identifies the local member by hostname pattern (or `DSH_PEER_DEVICE`), resolves every other member's live tailnet IPv4 (`tailscale status --json`, then `tailscale ip -4`, then the registry `ip`), validates the render with the peer package's own parser when a built peer package is available, and writes `$DSH_HOME/pairings.yaml` 0600 with the previous file backed up; a rejection or an absent registry leaves the existing document untouched and never fails the update.
3. The alias convention: a pairing uses the member's own name as its alias in BOTH files — the hub file carries `alias: macbook`/`peer: macbook`, the Mac's file carries `alias: macbook`/`peer: serverlocal` with `endpoint` at the hub — because the serving host resolves the incoming alias against its own table. Aliases are unique per host: a duplicated alias fails the load rather than letting one device's `create` hijack another's session.
4. Verify from either device: `ds peer status` prints the generated caller-role table, `ds peer status <member>` reads latch, model, budget, and asks, and `ds peer models <member>` / `ds peer switch <member> <provider/model>` exercise routing (when the host advertises the capability); `ds peer ask <member> "<message>"` (or the session's `peer` tool group: `peer_status`, `peer_ask(alias: "<member>", ...)`) drives the remote session.
5. Local acceptance without a second machine: `pnpm exec vitest run --config vitest.e2e.config.ts packages/api/peer/tests/pairings-roundtrip.e2e.ts` renders a scratch registry into two `$DSH_HOME`s and drives `peer.handshake`/`peer.create`/`peer.prompt` over loopback in both directions; `packages/api/peer/tests/pairings-generate.spec.ts` pins the registry validation, alias convention, idempotence, opt-out, and 0600/backup safety; `packages/api/peer/tests/routing-policy.spec.ts` and `host.spec.ts` pin the policy predicate, create-time evaluation, switch receipts, and attribution.
6. The remote instance receives the prompt, executes it under its own configured preset/permissions, and streams or returns the result back to the calling session.

### Safe keyless sandbox self-test

Run the whole check against an owned home and an owned port; nothing outside the sandbox should be read, written, or contacted:

1. Create a scratch root with `mktemp -d` and export `HOME`, `DSH_HOME`, `XDG_CONFIG_HOME`, `XDG_CACHE_HOME`, `XDG_DATA_HOME`, `XDG_STATE_HOME`, and `TMPDIR` inside it. Do not point any of them at the operator's home or reuse a live `$DSH_HOME`.
2. Seed a fresh profile: sourcing `scripts/install.sh` with `DSH_INSTALL_LIB_ONLY=1` defines the installer helpers and performs no install, after which `copy_profile_tree profile/web "$DSH_HOME/profiles/web" seed` copies the shipped tree and `seed_profile_home "$DSH_HOME/profiles/web"` writes the seed-once home files. The copy skips `node_modules`, so provision the seeded profile's dependencies the same way a normal install does (or link them from the already-provisioned checkout) before booting.
3. Write a fabricated `$DSH_HOME/pairings.yaml` (0600) with a caller-role entry (`alias`, `peer`, `endpoint: http://127.0.0.1:<port>`, `exposure: debug`, `create.agentPreset`) and, when exercising routing, a `routing` block. Fabricated aliases, a fabricated `cwd`, no real secrets, no operator settings.
4. Boot the harness with an empty environment so nothing inherits: `env -i` with only `HOME`, `DSH_HOME`, the four `XDG_*` directories, `TMPDIR`, and `PATH` set, then `node --import tsx/esm apps/cli/src/bin.ts web --host 127.0.0.1 --port <p> --no-open`. `--host 127.0.0.1` keeps the listener off the tailnet, and `--no-open` skips the browser.
5. Drive it through the same surface a controller uses: `peer.handshake` capabilities, one `peer.models` page, a create the policy refuses (assert no session and no binding appeared), a chain-only create, one short turn, a `selectModel` switch plus replay and reuse conflict, then a low `maxTotalTokens` on a fresh alias to observe the post-response stop and the subsequent `budget` prompt refusal.
6. Use only keyless, zero-price routes — the seeded keyless Kilo route and, as a fallback, the shipped `free` chain (zero-price, tool-capable, ungated, visible members with at least a 64k context window) — and never copy the operator's credentials into the sandbox. Keep the run at or below about 25 model requests; at 13–17k input tokens per tool-using turn that also bounds spend on any paid route a later catalogue change might introduce.
7. Shut the host down and delete only the owned scratch root. Keep the fabricated pairings document out of any repository tree.
