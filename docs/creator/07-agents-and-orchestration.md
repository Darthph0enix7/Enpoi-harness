# 07 — Agents & orchestration

How agent presets, seats, councils, the Oracle, and delegation work, and how to add, retarget, or disable each. Sources are cited repo-relative: `packages/…` is the harness repo, `profiles/<profile>/packages/…` is the installed profile (the fork packages live there, not upstream). Read the file you are about to edit before changing anything.

## 1. Presets — the session's agent identity

- Live declaration: a `preset-<id>` row in `$PROFILE/cordis.patch.yml` (`name: '@deepseek-ai/dsh-agent-preset'`; `config.plugins` is the composition — persona, tool rows, skill dirs, each row `- id: / name: / config:`, `disabled:` takes a JS expression). The `$PROFILE/presets/<id>/` dirs (`preset.yml` metadata + `agent.cordis.yml` composition) are the pre-merge source; the merged registry does not load them.
- Shipped presets (fork, order): `orchestrator` (default implementer, 1), `sysadmin` (host ops, 2), `creator` (harness-only repair, 3); the upstream `preset-standard`/`preset-ptc`/`preset-minimal`/`preset-cordis` rows are `disabled: true`. Upstream row contract: `packages/preset/agent-preset/src/index.ts:11-20` (`id`, `name`, `description`, `order`, `plugins`), registered via `ctx.agentPresets.register`, listed by `packages/preset/agent-preset-registry/src/preset.ts` (roster + `default`/`selectedDefault`).
- Switching: the composer agent picker (`conversation.input.agent`, ui-agent-preset) switches a session's preset mid-flight (idle recomposition; a session with history refuses a new-task default swap), the header label (`conversation.session.header.actions` id `agent-preset`) names the live preset, and Settings → Agent presets sets the new-task default. `enpoi-agent-switch` reads the original preset's composition (`agentPresets.readDocument`; the pre-0.1.7 local name was `read`), freezes the original persona bytes on the agent scope, and appends the new identity + doctrine as a trailing `agent-switch` runtime-context delta (order 900), so a switch preserves the cached prompt prefix (`profiles/web/packages/enpoi-agent-switch/src/index.ts:1-23`).
- Canonical main-agent shape (cache law): every main preset declares the same composition rows in the same order — identical tool array, identical prompt sections — and the only per-agent bytes are `persona.suffix` (rendered last at order 10200) and the `enpoi-orchestration` seat label, which only resolves group pre-attach (uniform across the main seats). The per-preset role doctrine — the orchestrator's delegation roster, research dials, and whiteboard rules — lives in that suffix only; the shared prefix stays role-neutral. A new preset created through the authoring UI copies the base composition byte-for-byte and rewrites only the suffix, so it inherits the canonical shape automatically. `tests/preset-prompt-parity.spec.ts` guards declaration parity, the byte-identical shared prefix, and menu equality; `scripts/preset-tool-inventory.mjs` diffs the wire roster (all three fixtures are the same 53 names).
- Per-seat restrictions are enforced at execution, never by tool absence: the composition mounts the same rows everywhere and the `enpoi-capabilities` pre-execute guard denies a seat's restricted calls (`SHIPPED_SEAT_TOOL_DENY` in `profiles/web/packages/enpoi-capabilities/src/policy.ts`; the document's `enpoi-orchestration.seatToolDeny` replaces a seat's list). The harness-authoring surface (`plugin_manager`, `cordis_inspect_list`, `cordis_inspect_query`) is creator-only: the `creator` tool group pre-attaches to the creator seat alone, so orchestrator and sysadmin never see the three schemas, and the seat guard backs that absence at pre-execute with a corrective reason. An operator who wants different restrictions configures `permissions.agents.<role>.tools` (doc 10, capability scoping) — but note that a permission `deny` is a *global-honesty* hide, so it also removes the tool from that agent's surface; use `seatToolDeny` when prefix parity must hold. Delegated children inherit their parent's preset, so the same guard refuses the trio for every orchestrator-/sysadmin-parented child; the child role tables name the trio (and `review_run`) so no child catalog carries a tool its guard refuses — `profiles/web/packages/enpoi-capabilities/tests/child-surfaces.spec.ts` is the guard, and the client parity spec cross-checks the same surfaces from the generated mirror.
- Create/retire: add or edit a `preset-<id>` row (copy a declaration, keep `config.plugins` minimal, add skill dirs via `skill-filesystem.config.customSkillDirs`); `disabled: true` retires it. Restart with `dsh restart --after-turn` from a hosted session (02). The **manual UI path** needs no restart: Settings → Agent presets → **+ New preset** clones a base preset — its composition, including the shared persona prefix, is copied byte-for-byte — into a new user preset with its own id, name, description, and persona suffix; Edit rewrites only name/description/suffix of user presets, Delete removes their row. Host side is `profiles/web/packages/enpoi-preset-authoring`: `presets.list|get|create|update|delete` over the fenced `/sidebar/presets` routes (`src/index.ts:1-16,240-306`); create writes through `configEditor.insert`, update through `configEditor.edit`, delete through `configEditor.remove` (`src/index.ts:54-61`) — the harness config editor (profile lock, recomposition validation, atomic write, Loader reconcile, rollback), so the picker and `agentPresets.list` see the change on the next read. `BUILT_IN_PRESET_IDS` refuse update/delete (`presets.ts:11-19,275-299`); shipped presets are edited in the profile declaration. Only the persona suffix is editable — `withPersonaSuffix` clones the plugin list and rewrites only `persona.config.suffix`, throwing when the base declares no persona row (`presets.ts:64-90`), and the UI only offers bases with `hasPersona` (`AgentPresetSection.tsx:325-333`), so the shared prefix stays byte-identical for prompt-cache parity (10). The button label is "New preset" beside one rendered plus icon (`locales.ts:100`), and the whole manual block is disabled until Coding Tools are on in General settings (`AgentPresetSection.tsx:99,122,180-193`).
- Failure modes: a composition that fails to mount is surfaced as `broken` on the roster; a row naming an unmounted plugin disables that row only. If a session "loses" a tool, diff the preset declaration's `config.plugins` against the plugin's row name before debugging deeper.

**Main-agent surfaces** (live declarations; all three mount `enpoi-tool-groups` — any group, static or on-demand, can be operator-disabled with `toolGroups.groups.<id>.enabled: false`, and the meta-tool itself with `capabilities.tools.tool_groups === false`; 05 §2/§6):

| Preset | Composition (`config.plugins`, condensed) | On-demand groups |
|---|---|---|
| orchestrator | persona, agent-instructions, first-run-context, bash/pwsh, fs, fs-search, jobs, skills (skill-filesystem + tool-skill), goal, plan-mode, orchestration (oracle, debug, tool-groups seat `orchestrator`), compaction (basic, compact, pruner), delegation (subagent `spawn` / `backgroundMode: continuable`, recovery control `send_message`/`list_agents`, workflow, ralph; fork/codex/claude-code off), ask-user, todo, web, presentation `both`, present | `peer`; `debug` pre-attached (shipped group default) |
| sysadmin | same rows as orchestrator (only the persona suffix and `seat: sysadmin` differ; `present` and the harness-authoring rows mounted for surface equality) | same |
| creator | same rows as orchestrator (canonical composition; only the persona suffix and `seat: creator` differ). Its doctrine stays harness-plane, and the harness-authoring rows (`plugin_manager`, `cordis_inspect_list/query`) are mounted on every main agent but runnable only on this seat (the execution guard above) | same |

## 2. Main agents vs subagents

- One session = one main agent (the preset composition). A subagent is a separate child session spawned through the `subagent` tool (`packages/subagent/tool-subagent/src/index.ts`), with its own log, tool surface, and durable id.
- Specialist roster (role personas, `packages/subagent/tool-subagent/src/index.ts:364-386`; the orchestrator persona names the same four):

| Role | Fleet group | Purpose | Child-surface restriction |
|---|---|---|---|
| `fixer` | specialists | bounded implementation: precise scoped edits, builds/tests | shared deny only |
| `explorer` | specialists | codebase mapping, symbol search, tracing; reports `file:line` | loses `edit`, `write`, `str_replace_editor` |
| `librarian` | specialists | external docs/API research with citations; runs the `research` skill end-to-end (dials, archived sources, anchored claims, verification) | keeps only `str_replace_editor` denied — the shipped baseline carries the research toolset (`bash`, `read`, `grep`, `write`, `edit`, `web_fetch`, `web_search`, `skill`, `todo_write`, `custom_research-fetch`, `custom_research-verify`, `subagent`); an operator `permissions.agents.librarian.available` entry replaces it wholesale |
| `designer` | specialists | UI/UX, styling, frontend craft | shared deny only |
| `oracle` | supervision | senior reviewer; tool-only, never spawnable (`NON_SPAWNABLE_BUILTINS`, `tool-subagent/src/index.ts:396`) | n/a — its own tool protocol |

- Child instructions: a delegated child's persona is the role registry's `persona` — the settings entry `roles[<id>].persona` when set, else the shipped `ROLE_PERSONAS` text — installed as the child's `deployment:persona-prefix` system-prompt section (which shadows the parent's persona for that child and blanks the inherited `deployment:persona-suffix`) by `applyChildComposition` (`packages/subagent/subagent/src/child-agent.ts:204-233`); the Oracle never goes through `subagent` and receives `ORACLE_PERSONA` from its own tool's spawn (`profiles/web/packages/enpoi-oracle/src/index.ts:40-52,721`). Dynamic → Roles reads the same effective text from `enpoiRoles.list`, never a client copy.
- Role selection: the `role` argument, else inferred from description+prompt (`tool-subagent/src/index.ts:850-871`); an unknown or tool-only id is refused listing the available roles (`:1055-1065`). The role persona replaces the parent's; every child also gets `SHARED_CHILD_DENY` (`:444-473` — no delegation, councils, oracle, goals, plan mode, workflows, `ask_user_question`, `send_message`, `interrupt_agent`, `list_agents`, and the guard-refused surfaces: the harness-authoring trio `plugin_manager`/`cordis_inspect_list`/`cordis_inspect_query` and `review_run`) and keeps the whiteboard tools (`SHARED_CHILD_KEEP`, `:483-488`). The background job controls are deliberately **not** denied: a child's bash command that outlives the executor timeout is promoted to a job owned by the child's session, the registry fences job access by owning session id, `job_output`/`job_list`/`job_kill` stay callable, and the child runtime context tells it to collect with `job_output (wait: true)` instead of re-running the command (`tool-subagent/src/index.ts:426-443`; `subagent/src/child-agent.ts:172-182`). The council seats, the Oracle review child, and the evidence research child carry the same guard-refused names in their own deny tables (`enpoi-council/src/core/fiber.ts`, `enpoi-oracle/src/index.ts`).
- Role tool surfaces are stored operator data and are audited at spawn: a name in `permissions.agents.<role>.available` or `roles[<id>].tools.available` that the live registry does not resolve is dropped with a `tool-subagent: role "…" stores unavailable tool "…"` warning (captured by `enpoi-diagnostics`) and the child spawns with the known subset, so a tool rename never bricks a role (`tool-subagent/src/index.ts:744-833`). The code-authored `toolFilter` config keeps the strict `tools.restrict()` throw for an unknown allow name.
- Enpoi delegation rows: `tool-subagent` (`provider: spawn`, `toolName: subagent`, `backgroundMode: continuable`); `tool-subagent-control`/`list-agents` are enabled for recovery continuation (`send_message` continues a child's durable session by id); fork, codex, and claude-code rows are `disabled: true`. New work is always a fresh child session — a follow-up that repeats the task is a NEW dispatch with the full context. Recovery is deliberate: a child that stopped before its end result names its session id and stop reason in the settlement notice, and `send_message` resumes that session with its history. The Oracle stays per-query persistent (its own plugin). Per-role model routes: `enpoi-orchestration.personas[<role>]` (§3); an empty entry (the shipped default) means the child inherits the parent route.
- Two shapes (`packages/subagent/subagent/README.md:12,59`): one-shot (single result, optional structured output) and continuable (later messages, interrupt; default `backgroundMode: one-shot`).
- Context inheritance is explicit, not implied: a fork child sees the parent's completed turns, a fresh child does not — the tool description changes accordingly (`tool-subagent/src/index.ts:260-284`). Children return a result, not intermediate steps.
- `maxDepth` per delegation (`tool-subagent/src/index.ts:95-102`): omit → Host depth setting, default `1`; `0` forbids delegation; integer → provider-enforced (mount fails loud if the provider has no `depthLimit`); `'provider-managed'` leaves it to the provider. This profile overrides the Host setting to `2` with a `subagent` row in the profile patch (`maxDepth: 2`), so main(0) → librarian(1) → readers(2) works for research fan-out; readers cannot delegate further.
- Parent-controlled spawn options: provider (`spawn` = in-process), label, `run_in_background` (continuable providers resolve at inbox acceptance; one-shot backgrounds become jobs), `quiet` (no parent-facing turn noise), and `agentOptions` (provider/model/effort for the child route) (`tool-subagent/src/index.ts:923-953`; `subagent/src/types.ts:56`; council spawn at `enpoi-council/src/core/fiber.ts:353-369`).
- Nested children exist: a continuable child can spawn its own children, and a settled resident (nested) parent keeps the waking flow for settlement notices because a quiet hold would strand its activation (`subagent/README.md:111`).

## 3. Seats and fleet routing

- A **seat** is a named model assignment key. Seat routing lives in `enpoi-orchestration.personas[<seatId>]` = `{ provider, model, reasoningEffort?, chain? }` (read freshest per spawn, `profiles/web/packages/enpoi-orchestration` consumers; e.g. council `core/fiber.ts:274-290`).
- Fleet groups render in fixed order (`packages/client/ui-brand-enpoi/src/client/role-registry.ts:50-58`): `supervision`, `specialists`, `council`, `custom` — plus one group per registered council and `UNGROUPED` for persona-only ids.
- Shipped seats per group: supervision — The Oracle, Context Keeper, CTX Summarizer; specialists — Fixer, Explorer, Librarian, Designer; council — Referee, Chair, and each council's debaters (role-registry.ts:152-183).
- Unassigned seats fall back two ways (`fleetSeatState`, role-registry.ts:89-92): `inherit` = the dispatching/session model; `builtin-default` = the seat's own plugin route.
  - **Keeper:** always `builtin-default: freellmapi/auto` (role-registry.ts:61,157) — it runs outside a conversation and has no parent model to inherit from. Do not expect it to follow the session model.
  - **CTX Summarizer:** designated seat, always rendered, `inherit` (session model). The footer states the economics: a different summarizer model loses the prompt-prefix cache and pays full input price for the region (`AgentModelsBody.tsx:217`); the panel explains all three states — assigned / inherit / built-in default (AgentModelsBody.tsx:8-18).
- To retarget a seat: Settings → Agent Models → Fleet Routing, pick a provider/model for the row (writes `personas[<id>]`); Reset clears it back to the default. A chain assignment resolves to the first enabled link at run time (compaction: `compaction-basic/src/settings.ts:138-161`; councils: `fiber.ts:238-272`).

## 4. Councils

- Two shipped councils, data-defined specs (`profiles/web/packages/enpoi-council/src/profiles/`):
  - **roundtable** — Skeptic / Architect / Pragmatist debate a decision; ledger kinds `crux` (C-, terminal `invariant|falsified|dissent`) and `risk` (R-); mandatory steelman before an attack flip; deliverable sections Decision / Options Considered / Evidence / Established Invariants / Binding Dissents / Action Items; defaults `defaultMaxRounds 6`, `stagnationLimit 2`, `challengeRound true` (`roundtable.ts:31-57`).
  - **chorus** — Visionary / Experiencer / Integrator in forest mode (SPROUT/BRANCH/FUSE/TENSION, nothing deleted); topological-saturation stopping; harvest with lineage (`chorus.ts:31-56`).
- Every council runs with two fixed arbiter roles, never seats: `referee`, `chair` (`enpoi-council/src/registry.ts:37`). Seat ids must be 2–32 chars `[a-z0-9_-]`; 2–8 contenders (`core/spec.ts:141,214`); ledger transitions are a DAG enforced by the engine, not the model (`spec.ts:51-64`).
- Tools: `roundtable` and `chorus` (one per enabled council), plus `council_register` / `council_list` (`tools.ts:174-176,256,421,522`). Registered councils get a tool named by their id.
- Running a council: the tool call is blocking; params come from `enpoi-orchestration.parameters.council`, read fresh per run (hot-swap) — `defaultMaxRounds` (6), `debaterTimeoutMs` (300 s), `runDeadlineMs` (30 min, on breach it skips to the chair), `evidenceBroker` (true), `evidenceTimeoutMs` (120 s) (`params.ts:22-38`; clamps at 48-62).
- **Evidence broker + vault:** debater fibers deny all retrieval tools and `bash` (`core/fiber.ts:93-149`, keep-list only whiteboard tools + `send_message` denied); a seat asks for ground truth with `NEED_EVIDENCE(target:, question:)` text lines. At each epoch boundary the engine batches the queue into ONE research child (`explorer` for codebase targets, `librarian` for external), one `SHEET n / CITATION / FACTS / CONFIDENCE` per question, committed to the append-only **evidence vault** as `F-n` before the referee pass (`core/broker.ts:120-132,193,236-245`; `core/vault.ts:10-18`). Missing/excess sheets are named failures, never silent; placeholder citations degrade to `unverified`.
- **Referee:** one flagship fiber per pass returns strict JSON only — `admissions`, `flips`, `directives`, `floor`, `scopeWarnings` (`core/referee.ts:78-94`). The engine applies every mutation and rejects steelman-less attack flips procedurally (`referee.ts:252-270`), unknown ledger kinds with a named reason (`referee.ts:289-296`), and a pass with no JSON is a hard handoff failure (retry once).
- **Chair:** compiles the deliverable with EXACTLY the spec's `deliverableSections`; a missing/bodyless section is a reported `ChairOutputError`, retried once, then mechanically compiled — never an empty answer forwarded (`core/chair.ts:1-21,58-84`; `core/engine.ts:544-567`).
- Register/retire a council: write `enpoi-orchestration.councils[<id>]` (same shape `council_register` validates; `stoppingPolicy` + `chairTemplate` required) or use `council_register`. A settings entry with a built-in id overrides it; `disabled: true` retires it (tool disappears) — `registry.ts:1-19,306-335`. Invalid entries stay visible with their exact validation problem in the council UI; nothing is skipped silently.

## 5. The Oracle

- `oracle_review` consults a senior reviewer child: call #1 of a user query is fresh and self-contained; follow-ups are deltas in the same fiber. Blocking by default, `background: true` delivers the verdict as a message (`enpoi-oracle/src/index.ts:569-595`).
- Lifecycle: fiber resets at each new human user message; one consultation per session at a time (single-flight mutex returns `CONCURRENT_CALL_REJECTED`); timeout default `120_000 ms` via `parameters.oracle.timeoutMs`, resolved per call; on timeout the child is NOT cancelled and its verdict is delivered late as a message (`index.ts:629-638,647-663,685-690,216-218,864-867`).
- Surface: read-only review; the oracle may delegate (subagent tools) and use `request_evidence(target, question)`, which spawns one research child and returns a cited fact sheet (`index.ts:53-72,74-102`). Verdict JSON `{approved, concerns, unverified, blockers}` must be last (`index.ts:48-49`).
- Model: `personas.oracle` (provider/model/effort/chain). With a chain, a failed attempt disposes the child, respawns the SAME initial package on the next link, and fails open to exactly one wait without a chain (`index.ts:740-770`).

## 6. Delegation rules

- **Dispatch doctrine (orchestrator persona suffix):** scoped, simple, clearly implementable work goes to a `fixer` readily — the orchestrator keeps the complex reasoning, research, context, and understanding, and uses the fleet liberally so its own context stays lean. Dispatches are background by default; `run_in_background: false` only when the very next step needs the answer. Parallel work is one `subagent` call per specialist in the same assistant message — several specialists at once, even several of the same role. New work is always a fresh, self-contained dispatch; a follow-up to a finished task is a NEW dispatch carrying the full context, including what the previous child reported and what has changed. Continuation by id is for recovery, not a second dispatch lane: a child that stopped before its end result names its session id and stop reason in the settlement notice, and `send_message` continues that session with its history when its context is worth resuming. While children run the operator keeps interacting; the parent ends its turn with a short report of what it dispatched and what each child should return.
- **Role charters (the four spawnable specialists):** `fixer` — scoped implementation, bug fixes, focused edits, builds and tests; `explorer` — codebase mapping, symbol search, file discovery (never mutates); `librarian` — web search, documentation, library research, external APIs, reported with citations; `designer` — UI/UX, responsive styling, design-system tokens. Name the role first in the dispatch description (`"librarian: research X"`, `"fixer: implement Y"`) — that is how the child receives its persona; the roster is authoritative, so never search the repository or harness sources to discover which agents exist.
- **Whiteboard & context (orchestrator-owned):** before dispatching several children or any long-running task, the orchestrator authors and pins what the fleet must not have to repeat — current task state, key decisions, invariants, file paths — with `whiteboard_write`/`whiteboard_pin`, and updates or unpins as work lands; a tight board replaces repeated context in every Task Card. Children read the board but never author it (lineage gate enforced); the background context keeper maintains session checkpoints on its own, so neither parent nor child duplicates a brief by hand. Board storage, scope resolution (global → project → parent session → session), and stale flags: 08.
- **Programmatic tool execution (run_code):** for batch operations, loops across files, or data transformations, call `run_code` to execute a TypeScript program in ONE turn instead of serial turn-by-turn tool calls. Subagents (`fixer`, `explorer`) also have `run_code` available natively. Three key conventions: (1) each call runs in a fresh isolated Node process — no state carries between calls, and never park state in `/tmp`; (2) erasable TypeScript only (no `enum`, namespaces, or runtime-only TS syntax); (3) arguments must be lossless JSON — do not pass `undefined` inside objects (rejected outright by the bridge).
- **Research delegation (this profile):** anything needing the live web — news, pricing, docs, comparisons, releases, "what is the latest…" — goes to ONE `librarian` with the question and a dial: `lookup` (1–3 fetches, inline, <1 min) / `quick` (2–4 sources, short cited answer) / `standard` (default: 5–10 sources, 1–2 readers, cited report) / `deep` (15–25 sources, 3–6 readers, dossier) / `exhaustive` (deep + adversarial counter-searches). The dispatch prompt names the question, the dial, the freshness horizon, the source/time budget, and the deliverable (`librarian: research — <question>`; template in `$PROFILE/skills/research/SKILL.md`). The librarian runs the `research` skill end-to-end — archives sources with `custom_research-fetch` (the page text never enters the caller's context), writes anchored claims, runs `custom_research-verify` to PASS, and returns the cited answer plus the run-dir path. The main session never fetches, saves, or extracts; deep and exhaustive runs fan out reader children under the librarian.
- **Budgets:** every delegated child gets a standing clause — `CHILD_TOOL_BUDGET = 20` tool calls is a ceiling for exploration, not a counter to satisfy; report best evidence or report what is missing (`packages/subagent/subagent/src/continuation-messages.ts:99-120`). The clause is appended on every path (continuable, background, foreground — `tool-subagent/src/index.ts:1193,1212`).
- **Lifecycle (spawn → run → settle):** spawn validates the role and provider capabilities, snapshots the delegated permission state, and appends a `subagent/catalog` fact to the parent after admission (one-shot after the provider returns, continuable after inbox admission — `subagent/README.md:113`); a failed spawn rolls back unpublished resources and publishes no catalog fact. Run happens in the child's own durable session/log; background (continuable) is the default, `run_in_background: false` waits and returns the report in the tool result. Settle injects the one notice.
- **Ceilings:** `maxDepth` (host `subagent` settings default `1`; this profile sets `2` — main → librarian → readers; a tool row may set an integer or `provider-managed`, `0` forbids delegation), `maxActiveSubagents` default `8` live continuable children (capacity refuses with `ACTIVATION_LIMIT_REACHED` and does not queue — wait for a settlement notice before retrying; slots are process-local — `subagent/README.md:47-55`), plus the 20-call budget clause. The orchestrator persona suffix states the same doctrine (8 live children, not queued, track settlement notices / `list_agents` running rows), and the rejection text repeats it (`packages/subagent/subagent/src/continuation-activation.ts:43-51`).
- **Quiet single delivery:** foreground delegation returns one result; background/continuable settlement injects ONE notice into the parent containing the outcome line and the child's closing report only (reasoning and tool blocks stripped) — `continuation-messages.ts:129-199`. A settlement that lands while the parent is parked/reverted is held quietly in the durable next-turn inbox for a root parent (`subagent/README.md:111`). A turn abort (`cancel`) clears only **user-sourced** inbox items; settlement notices, adjacent-agent relays, and job-completion notices already spliced into the inbox survive to the next turn, each user input canceled with its own durable record and no auto-wake (`packages/core/agent-loop/src/inbox.ts:100-115`; regression `packages/subagent/subagent/tests/cancel-preserves-settlement.spec.ts`).
- **Recovery continuation (this deployment):** children do not stream intermediate steps back, but the control tools are enabled. A child that stopped before its end result names its session id and stop reason in the settlement notice; `send_message` to that id cold-resumes the same durable session with its full history (an idle child; a working one receives the message at its next step). `list_agents` lists a parent's continuable children by id, bounded: `limit` defaults to 20 and is capped at 100, rows order running-first then inactive most-recent-first (descendants keep tree pre-order), and an omitted-row footer names shown/total plus the running/inactive split and a hint to raise `limit` or narrow `scope` (`packages/subagent/tool-subagent-control/src/list-agents.ts:24-28,131,181-198`). New work is still a fresh dispatch — continuing an old child is the deliberate exception for recovery or an operator-requested follow-up, never the default path for a new task. The Oracle keeps its own single-flight mutex (one consultation per session at a time).
- **Stopping:** the composer's Stop (✕) is `detach` — the turn stops, live continuable descendants keep running; "Stop all agents" is `stop-all` — `enpoi-cascade` interrupts every live continuable descendant under ancestor authority; a revert interrupts only descendants spawned inside the reverted span. Interrupt is PARK-semantic (current turn cancelled; activation stays resident). A parked worker resumes when the parent `send_message`s its id with the next instruction; the human can also continue it from its sidebar chat tab (host Queue/Steer prompt).
- **Approvals:** a child's ask forwards to the nearest live root (04 §6); the child's scope is fixed at spawn and cannot widen from inside (the delegation-scope statement, `subagent/README.md:169`).
- **Nested children:** depth is capped by `maxDepth` (shipped default 1; this profile 2, see §2); stopping a parent parks the descendant tree — the cancel cascade recursively enumerates the whole session tree, including continuable grandchildren (`profiles/web/packages/enpoi-cascade/src/index.ts:58-114`).
- **Failure forwarding:** a failed child never reports success — `settlementSummary` names the ending (aborted / max-tokens / refusal / error / abnormal) and, for every unfinished ending, the session id to inspect or continue; providers append the failure detail plus any preserved partial answer to the error (`continuation-messages.ts:129-156`; `tool-subagent/src/index.ts:171-180`).
- **Keeper exemption:** the context keeper is not a subagent, so the ancestor-cancel cascade never enumerates it — it keeps running through stop-all/revert cascades (`enpoi-cascade/src/index.ts:21`; doc 34 invariant I9).

### Tier workflows

The operator invokes a guided workflow by asking for a tier (for example "tier 1" or "tier 3") in the request; the skills are operator-editable data at `$PROFILE/skills/tier{1,2,3}-workflow/SKILL.md`, read per request — edit the file and the next request sees it (no build, no restart), and `enpoi-orchestration.capabilities.skills['tier1-workflow']` (etc.; §8) removes or restores the skill in the catalog. Scope is per request: a tier governs the current request only, a new request starts from the default behavior unless the operator invokes a tier again, and invoking another tier for the same task replaces the active workflow. State lives in harness-native artifacts — whiteboard entries (`whiteboard_write` / `whiteboard_pin`, visible to spawned children) plus the `todo_write` list.

- **Tier 1 (supervised):** Oracle review of the drafted plan (`oracle_review`) before any code, implementation, then a final Oracle consensus before shipping — actionable issues are fixed first.
- **Tier 2 (ideation → plan):** mandatory `roundtable` on the vision, its council report translated into a technical plan, Oracle review of that plan, implementation, then a final Oracle review.
- **Tier 3 (all-out):** continuous Oracle supervision across implementation milestones, plus a mandatory `roundtable` whenever ambiguity blocks the path.
- All three tiers carry a **Delegation & Offload** section: keep the main session lean, dispatch bounded work to `fixer`/`explorer`, route web research to ONE `librarian` with a research dial (standard default), and give every dispatch the full context it needs (fresh session, self-contained brief).

The upstream `context-lens` "Request Context" view is registered but hidden by default here (`enpoi-orchestration.uiPreferences.hiddenSurfaces.views`, `packages/client/ui-conversation/src/client/hidden-surfaces.ts:18`).

## 8. Enable / disable switches

- Capabilities Control Center (`enpoi-orchestration.capabilities`) is the master switchboard (`profiles/web/packages/enpoi-capabilities/src/state.ts`, `types.ts:44-70`): `skills[<name>] !== false` strips a skill from the catalog AND shadows it pre-dispatch; `tools[<id>]` false strips the tool from the model-facing list and denies it; `mcp[<id>] === true` is required to mount an MCP server.
- Protected infrastructure cannot be disabled: `enpoi-contracts`, `enpoi-context-keeper`, `enpoi-cascade`, `enpoi-living-brief`, `read`, `glob`, `grep` (`types.ts:27-35`).
- The keeper's own tool flag is `capabilities.tools.keeper` (default true); disabled means prose distillation and claims extraction are skipped and consumers degrade to the deterministic fold (`enpoi-context-keeper/src/index.ts:102-113,586-588`).
- A registry role is hidden from the fleet with `roles[<id>].seat: false` or `disabled: true`; `null` deletes it (`role-registry.ts:203-261`). A role may carry `tools.available` (a tool-id allowlist for its persona, `role-registry.ts:253-257`) — a per-role availability layer on top of the profile defaults and before session overrides. A tool-only role (Oracle, `spawnable: false`) is never matched by delegation text (`tool-subagent/src/index.ts:340-350`).
- **MCP on-demand:** a catalog server's `mode` defaults to `always-on`; `on-demand` servers are never auto-connected (`profiles/web/packages/enpoi-capabilities/src/index.ts:87-99`; `mcp-mounts.ts:91-97`). The agent mounts one for its own session with the `mcp` tool — actions `list` / `mount` / `unmount`, `server` is the catalog id (`index.ts:761-813`); its shipped policy row is `allow` because `list` is read-only and mount/unmount only touch servers the operator already configured and allowed, scoped to the calling session and reversible — the mounted server's own tools keep their own rows (`policy.ts:169-173`). One shared mcp-client fiber per server serves every session that mounted it, and it disposes only when the last session unmounts (`index.ts:556-618,653-666`); each session's mounted set is durable (`mcp/mounts` event → `mcpMounts` projection, `mcp-mounts.ts:32-77`) and is released at session end (`index.ts:710-724`). An on-demand server this session has not mounted is filtered from the advertised surface (`index.ts:419-450`) and denied at pre-execute as the backstop for in-flight turns (`index.ts:1361-1376`). Doctrine: "a mount made for continuing work stays mounted; a one-shot errand unmounts when it is done; when unsure, leave it mounted" (`index.ts:858-866`). A skill's `mcp: [server]` frontmatter mounts on load (`index.ts:814-855`); the session header chip lists this session's mounts and unmounts from its popover (`$REPO/packages/client/ui-brand-enpoi/src/client/McpMountsChip.tsx:1-7,124-160`).
- **Permissions matrix presentation** (09): the Permissions window reads every live registered tool name and folds families derived from the shipped tool-group catalog — one aggregate row per enabled group with at least two same-policy members (Goals, Councils, Jobs, Workflows, Whiteboard, Memory, Peer interconnect, Debug & observability, Creator (harness authoring)) — while a member whose shipped policy differs stays its own concrete row; it labels the `mcp` tool "MCP servers (mount / unmount)", folds every concrete `mcp__<server>__<tool>` under its server row, and renders "All MCP tools" as the derived aggregate master (the master and each family own no settings key; their chip fans the chosen policy out to the concrete keys) (`$REPO/packages/client/ui-brand-enpoi/src/client/permissions-model.ts:319-362,434-472`). The matrix also lists custom-tool rows automatically from the live registry (05 §8).

## 9. Failure modes → fix

- **Evidence:** incidents in `$DSH_HOME/diagnostics/incidents.sqlite` (sources: logger sink, plugin lifecycle FAILED, session-event error paths, client reports; `diagnostics_report` folds them with stable codes/fingerprints — `profiles/web/packages/enpoi-diagnostics/src/index.ts:6-13`); per-plugin logs `$DSH_HOME/logs/enpoi-*.log` (cascade, keeper, council, git, file-revert, runtime-probe) plus `$DSH_HOME/logs/startup-*.log`; service stdout in the journal. The Cordis logger only buffers, so plugin diagnostics are those files.

| Symptom | Cause | Fix |
|---|---|---|
| Seat runs on an unexpected model | No assignment → inherit, or stale `personas[<id>]` | Agent Models → Fleet Routing: assign or Reset the row; check the row's state label |
| Council tool missing | Council retired (`disabled: true`) or invalid entry | Council list shows the validation problem; fix the spec or remove `disabled` |
| Council produces empty deliverable | Chair output failed shape validation and mechanical compilation also failed | Check the council log (`$DSH_HOME/logs/enpoi-council.log`); inspect ledger/referee records in the result |
| `oracle_review` blocked (`CONCURRENT_CALL_REJECTED`) | Another consultation in flight for the session | Wait for the verdict or the timeout; the child is not cancelled |
| Child floods the parent with messages | a child calling `send_message` per finding | children keep `send_message` denied (`SHARED_CHILD_DENY`), so intermediate traffic cannot happen; the 20-call budget clause is appended |
| Keeper still runs after stop-all | Cascade exemption (by design) | Disable it via `capabilities.tools.keeper` if truly unwanted |
| Preset missing after install | `preset-<id>` declaration absent or `disabled: true` | `dsh plugin list`/`cordis_inspect` for the row; see 02-install-and-update |
| Child fails to start | role unknown/tool-only, provider capability missing (`continuable`, `depthLimit`), or capacity `ACTIVATION_LIMIT_REACHED` | read the tool error verbatim (it names the role list or capability); `session_debug` digest → recent tool calls; `diagnostics_report`; check the preset declaration's delegation rows |
| Child stuck (running, no progress) | long turn, waiting on an approval, or a parked activation | `session_debug` digest (`state.activeDescendants`, `subagentTree`); Subagent Sessions tab; QueueDock; then Stop all parks it — `$DSH_HOME/logs/enpoi-cascade.log` names refused interrupts |
| Approval not forwarded | root not live, root mode not interactive/full-access, or the ask undeliverable (fails closed) | 04 §6; `session_debug` `pendingInteractions`; Live Debug ask buttons; confirm the root session is open |
| Tool missing for a role | on-demand group not attached, capability disabled, role allowlist/deny, or the preset row unmounted | `tool_groups list`; 05 §4/§9; `enpoi-orchestration.roles.<id>.tools.available`; diff the preset declaration |
| MCP tool returns "on-demand and this session has not mounted it" | the server's catalog `mode: on-demand` and no mount in this session | call `mcp` action `list`, then `mount` with the catalog id; the mount applies next turn (07 §8; 10 "MCP servers: on-demand vs always-on") |
| Custom tool fails or asks on every call | malformed record/placeholder, or the `custom_<id>` permission row inherited `ask` | read the plugin stderr line; fix the record in Dynamic → Skills & tools; set the row in Permissions (05 §8) |

## 10. Device-to-device & peer-to-peer agent communication

Cross-device agent communication allows an agent on one machine (e.g. laptop) to delegate tasks, query state, or collaborate with an agent running on another instance (e.g. serverlocal):
- **Architecture**: `@deepseek-ai/dsh-api-peer` exposes `ctx.peerService` with the `peer` namespace (`handshake`, `state`, `create`, `prompt`, `cancel`, `answer`, `page`, `follow`). It is an API-level peer-to-peer bridge over secure HTTP/WebSocket transport (such as Tailscale mesh or local network).
- **Configuration & documents**:
  - `$DSH_HOME/pairings.yaml` (0600 file, reloaded on mtime change): human-edited table mapping peer aliases to remote endpoint URLs and authentication tokens.
  - `$DSH_HOME/peer-state.json`: machine-written runtime bindings and active session associations.
- **Tool surface (`peer` on-demand group)**:
  - `peer_status`: inspect configured peer connections, latency, and remote session state.
  - `peer_ask`: dispatch a query or prompt to a paired remote agent, optionally targeting an existing remote session or spawning a fresh session.
  - `peer_asks`: poll active cross-device requests and pending responses.
  - `peer_answer`: reply to an incoming request from a remote peer.
  - `peer_cancel`: abort an in-flight cross-device task.
- **Testing recipe between devices**:
  1. Ensure both devices have the harness running and reachable (e.g. over Tailscale).
  2. On Device A (e.g. MacBook), configure `$DSH_HOME/pairings.yaml`:
     ```yaml
     version: 1
     device: macbook
     pairings:
       - alias: server
         peer: serverlocal
         endpoint: "http://100.122.163.25:3080"
         exposure: debug
         create:
           agentPreset: orchestrator
     ```
  3. On Device B (e.g. serverlocal), configure `$DSH_HOME/pairings.yaml`:
     ```yaml
     version: 1
     device: serverlocal
     pairings:
       - alias: macbook
         peer: macbook
         exposure: debug
         create:
           agentPreset: orchestrator
     ```
  4. In a session on Device A, attach the `peer` group (`tool_groups attach peer`) or execute `peer_status`.
  5. Call `peer_ask(alias: "server", message: "Inspect serverlocal GPU and Docker status")`.
  6. The remote instance receives the prompt, executes it under its own configured preset/permissions, and streams or returns the result back to Device A's session.
