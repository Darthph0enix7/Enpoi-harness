## Pre-sign-off fix wave

The post-2.92 pre-sign-off wave (owner-reported UI defect plus the fix-9 read-only audit's findings), all landed before the sign-off: source-built `base+g<sha>` installs are offered their next release again (the comparator treats `+` as build metadata, never a separator, so a differing commit reaches the version comparison instead of `unknown`); a rolled-back apply's archived staged tree is validated by `updateCheck.apply` (distinct `staged-tree-missing`) and the record's `staged` flag now means "a complete staged update is ready to apply", so Retry/recover/Update-now route into a fresh prepare instead of replaying a doomed apply; `--cancel` and the plugin's cancel relay treat terminal marker phases as authoritative (a run finishing inside the cancel window reports `noop`/already finished, never `cancelled`, and a terminal record is never overwritten), and the engine defers INT/TERM once `switching` is written; `start` is single-flight so two Update-now clicks in the probe window launch one engine; engine attach/cancel eligibility now requires the same marker/log progression window the plugin uses (a recycled pid behind stopped files is never signalled or attached to); and a terminal cancelled/failed/rolledback record with a `current` status renders as history (Up to date + Check) instead of the sticky "Update cancelled / Retry" row the owner hit on the Mac — a no-op prepare (already up to date, nothing staged) ends as a terminal success the surfaces present as up to date.

## Live incidents found and fixed

| # | Incident | Symptom on a device | Root cause | Fix |
|---|---|---|---|---|
| 1 | Reader-held lock deadlock (macOS / lock rung) | A terminal `dsh update` and a UI apply collided over `.update.lock.d`; the apply refused with `another update is already running (PID …); wait … or remove … if it is stale`, and the engine never broke a stale lock; the subscriber could end up owning the lock the UI needed | Attach competed for and held the lock; a dead-owner mkdir lock had no recovery path | `bb12abc64c` — attach probes "held lock + live marker pid" read-only and subscribes before any lock attempt (never creates/reclaims/holds); the mkdir rung verifies the recorded pid with the zombie-aware probe and reclaims dead/zombie/unreadable owners with one warning; a live pid is never broken |
| 2 | macOS double-acquire apply deadlock | The apply refused against itself on the mkdir rung (`another update is already running` naming its own process) | `do_apply_staged` re-entered `acquire_update_lock` after `do_update` had taken it; the flock rung silently re-acquired, the mkdir rung saw its own live pid | `bb12abc64c` — `UPDATE_LOCK_OWNED`: one lock per process, a re-acquire is a no-op |
| 3 | Stale records with no escape | A dead run's record kept reading as active (recycled pids) or blocked start/apply with no way out | Liveness was pid-only and the gates had no engine-truth comparison; no recovery action existed | `5980d64c93` — one liveness truth (live non-zombie pid AND log movement within 5 min; terminal phases never live), self-heal on every `run`/boot/gate, `updateCheck.clearStale` (refuses while anything is live, never touches the engine marker/staged tree), and the UI's "Clear update state & retry" (re-applies without re-download when the staged marker survives) |
| 4 | Wasted ~300 MB divergence fetch | The PC's 2.88 run downloaded the whole prebuilt tarball (304 MiB in 301 s) and then fell back to the source build | The release (2.87) no longer matched the moved beta head, and divergence was detected only after the fetch | `f945ed1b50` — the release commit is resolved and compared with the channel head before any bytes are fetched; a divergent release is skipped up front with one warning; an unresolvable side keeps the download path. **Superseded by the prebuilt-only policy (incident 8): a published release is always installed; head-ahead is informational.** |
| 5 | Bare-base source stamp loop | A source-built install read `0.1.7-enpoi.2`, the UI kept offering the same release forever, and `dsh --version`/identity assertions were meaningless | The source transport kept only the tree's package.json base; nothing distinguished a rolling channel build from its release | `f945ed1b50` + `dae6d0132e` — source builds stamp `<base>+g<short sha>` in the tree dir, marker, install-state, CLI, health, and client build env; the check compares commits before versions (`commitsMatch`, ≥ 7 hex chars, prefix-compatible); the client renders the `(source build)` qualifier |
| 6 | Pill suppressed by a stale landed-success record | After any successful update, every later available release showed no pill (the settings row kept working) | `showPill` treated ANY terminal-success record as "just landed"; `run.json` keeps the previous success forever | `93fd62724b` — the guard is scoped: a success suppresses only while it landed the release the status still offers (`landedOffering = run.target === latest.version`); a newer catalog version re-arms immediately |
| 7 | Stale "Updating…" frame | After a successful update the client kept rendering an executing run | The run record survived the service restart as executing, and reconnect only re-read the run when a pending marker existed | `93fd62724b` — reconnect re-reads the run unconditionally, and a status read reporting the install `current` reconciles an executing record on the spot |
| 8 | Client-machine source build on update | `0.1.7-enpoi.2.109 → 2.112` logged `prebuilt: release v… was built from … but the stable channel resolves to …; skipping the prebuilt download and building from source`, then ran `pnpm run build` for 416 s on the server | The release for the moved head was still a draft; the divergence pre-check treated head-ahead as a reason to skip the published release and build the branch | Prebuilt-only policy: a published release is always installed, head-ahead is one informational line, and there is no automatic source fallback. No release/unusable asset errors with the publish/`--source` remedy; only `--source`/`--no-prebuilt` builds. The no-op check compares against the newest published release, so a second `dsh update` reports up to date |
